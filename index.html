jXchange API Passthrough & Middleware Gateway

Give fintech partners clean JSON REST access to Jack Henry Silverlake and Symitar cores without handing them a SOAP toolkit, the institution's consumer credentials, or a new vendor in the data path.

Why this exists

jXchange is the integration bus in front of Jack Henry cores: SOAP 1.1, enterprise XML envelopes, WS-Security headers, mTLS certificates, and static IP allowlists. Every partner integration rebuilds the same translation layer, badly. This template deploys that layer into the institution's own AWS account from one file, so the bank keeps custody of its credentials and its core.

SOAP in, JSON out

Vendors call GET /v1/accounts/{id}. The gateway builds the envelope, signs the call with the bank's consumer credentials, and normalizes the response.

Deny by default

Each API key is locked to a persona. Anything outside that allowlist is pruned before the response leaves the gateway. Unknown personas fail closed.

No vendor footprint

Lambda, API Gateway, DynamoDB, Secrets Manager, and a NAT gateway with a static Elastic IP. No servers to patch, no data warehouse, no loan data at rest.

Self-serve onboarding

The institution shares a role-scoped invite link. The partner generates its own key in seconds. The server chooses the persona, never the client.

API surface

All /v1/* routes require x-api-key. The portal and health check are the only unauthenticated routes. Writes are not implemented: POST, PATCH, PUT, and DELETE return 501.

Core status and transaction type codes are returned as the core's canonical values. Resolve them with jXchange SvcDictSrch; the gateway deliberately keeps no field or code dictionary that would drift from the core.

Deploy in one command

Run this in AWS CloudShell, in the institution's account. It asks for the jXchange endpoint, routing ID, and consumer credentials, generates three role invite codes, deploys the stack, and prints the portal links and the static egress IP to whitelist.

bash <(curl -sSL https://raw.githubusercontent.com/Spuds0588/jXchange-API-Passthrough-Middleware-Gateway/main/deploy.sh)
Read the limitations before promising a partner anything. The maintainers have no Jack Henry access and no AWS account for this project, so the SOAP shapes are built from the published jXchange reference and exercised against a local fake. A real institution must confirm its response shapes, credentials, and network allowlist. The gateway is read-only by design; money movement is out of scope until a separate, reviewed design exists.

Frequently asked questions

What does this gateway actually do?

External partners send JSON REST requests with an x-api-key. The gateway builds a jXchange SOAP 1.1 envelope, adds the institution's consumer credentials, calls the core over mTLS, parses the SOAP response, and returns normalized JSON. It stores no loan or account payloads.

Does it support money movement or account changes?

No. The MVP exposes AcctInq, AcctHistSrch, and CustInq only. Write methods return 501, because silently accepting a write the core never applied is worse than refusing it.

Where does it run and who holds the credentials?

In the institution's AWS account, deployed from one CloudFormation template. The institution supplies its own Jack Henry consumer credentials and optional client certificate through Secrets Manager. There is no vendor-hosted service and no shared multi-tenant API.

Why is a static egress IP needed?

jXchange endpoints commonly allowlist source addresses. The template provisions a VPC, NAT gateway, and Elastic IP so the institution can whitelist a single stable address rather than a changing set of Lambda addresses.

Is this an official Jack Henry product?

No. It is an independent, community-maintained open-source template, not affiliated with or endorsed by Jack Henry & Associates. Confirm schemas, credentials, and approvals with your institution and Jack Henry contacts.

How do I contribute or report a problem?

Open a GitHub issue with a minimal reproduction and sanitized logs, or send a pull request with a regression test. The maintainers have no Jack Henry tenant, so a real deployment report is more valuable than a speculative patch.

Community maintained

This is shared infrastructure, not a paid product. Every real deployment is also a test, so issues and pull requests are the roadmap:

  • File a bug with a minimal reproduction, the commit you tested, and sanitized logs.
  • Request an improvement — especially a real jXchange response shape we cannot see.
  • Send a pull request with a regression test and the docs updated in the same change.
  • Read the contributing guide before you start.

Privately patched forks are discouraged: upstream the smallest fix so the next institution benefits. Never include API keys, invite codes, certificates, account numbers, or customer data in an issue, pull request, screenshot, or log.
